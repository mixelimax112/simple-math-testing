### Что показывать:

### Что рассказывать:

**"Для авторизации я использую JWT токены - это современный стандарт для REST API."**

**Как это работает:**

1. **Регистрация** (`POST /api/auth/register/`)
   - Пользователь отправляет email, пароль, имя
   - Пароль автоматически хешируется (не храним в открытом виде!)
   - Создается новый пользователь

2. **Вход** (`POST /api/auth/login/`)
   - Отправляем email и пароль
   - Получаем два токена:
     - **Access token** (живет 1 час) - для API запросов
     - **Refresh token** (живет 7 дней) - для обновления access токена

3. **Использование**
   - Каждый запрос содержит заголовок: `Authorization: Bearer <token>`
   - Сервер проверяет токен и идентифицирует пользователя


### Автоматический расчет цены (покажите код):

```python
    nights = (self.check_out - self.check_in).days
    return self.listing.price * nights
```

**"При создании бронирования цена рассчитывается автоматически: количество ночей умножается на цену за ночь."**

**"Я реализовал комплексную систему валидации, которая проверяет:"**

1. **Даты корректны:**

2. **Нет пересечений с другими бронированиями:**

## 🧩 9. БАЗОВЫЕ КЛАССЫ И ПЕРЕИСПОЛЬЗОВАНИЕ КОДА (3-4 минуты)

### Что показывать:
Откройте `core/models.py`

### Что рассказывать:

**"Я следовал принципу DRY (Don't Repeat Yourself) - создал базовые классы, которые переиспользуются во всех моделях."**

### 1. TimestampedMixin (строки 4-10):

```python
class TimestampedMixin(models.Model):
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)
    
    class Meta:
        abstract = True
```

**"Этот миксин добавляет к модели два поля:**
- `created_at` - автоматически заполняется при создании
- `updated_at` - автоматически обновляется при изменении

**Используется в ВСЕХ моделях проекта. Вместо того, чтобы копировать эти два поля в каждую модель, я просто наследуюсь:"**

```python
class Listing(TimestampedMixin):  # И поля уже есть!
    # остальные поля
```

### 2. SoftDeleteMixin (строки 13-18):

```python
class SoftDeleteMixin(models.Model):
    deleted_at = models.DateTimeField(null=True, blank=True)
    
    class Meta:
        abstract = True
```

**"Это реализация мягкого удаления (Soft Delete)."**

**Проблема с обычным удалением:**
- Пользователь удалил объявление
- Но есть активные бронирования с ссылкой на это объявление
- При жестком удалении потеряются данные!

**Решение - мягкое удаление:**
- Запись не удаляется физически из БД
- Просто помечается полем `deleted_at`
- Можно восстановить, если нужно

### 3. SoftDeleteManager (строки 21-25):

```python
class SoftDeleteManager(models.Manager):
    def get_queryset(self):
        return super().get_queryset().filter(deleted_at__isnull=True)
```

**"Это кастомный менеджер, который автоматически фильтрует удаленные записи."**

**Без менеджера:**
```python
Listing.objects.all()  # Вернет ВСЕ, включая удаленные
```

**С менеджером:**
```python
Listing.objects.all()  # Вернет только неудаленные (deleted_at=None)
```

**"Использование всех миксинов вместе (покажите listings/models.py, строка 9):"**

```python
class Listing(TimestampedMixin, SoftDeleteMixin):
    # Сразу получаем:
    # - created_at
    # - updated_at
    # - deleted_at
    # - и кастомный менеджер
    
    objects = SoftDeleteManager()
```

## 💬 ОТВЕТЫ НА ВОЗМОЖНЫЕ ВОПРОСЫ

### "Почему Django, а не FastAPI?"
"Django предоставляет больше из коробки - админ-панель, ORM, аутентификацию. Для CRUD API с административной панелью Django - оптимальный выбор. FastAPI быстрее, но требует больше настройки."

### "Почему MySQL, а не PostgreSQL?"
"Оба отличные выборы. MySQL проще в настройке и более распространен. Для этого проекта функционала MySQL достаточно. PostgreSQL был бы лучше, если нужны JSON запросы или full-text search."

### "Как масштабировать этот проект?"
"Можно добавить:
- Redis для кеширования
- Celery для фоновых задач
- Nginx как reverse proxy
- Горизонтальное масштабирование через Docker Swarm или Kubernetes
- CDN для статики и фото"

### "Есть ли тесты?"
"В текущей версии нет unit-тестов, но архитектура позволяет их легко добавить. Каждое приложение можно тестировать независимо благодаря модульности."

### "Почему не использовали GraphQL?"
"REST API проще для стандартных CRUD операций. GraphQL оправдан, когда у клиента много разных запросов с разной структурой данных. Здесь REST достаточно и понятнее."
